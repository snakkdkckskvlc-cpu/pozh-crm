## Зачем этот документ и что будет, если его не сделать

**Тип поля в Twenty нельзя изменить после создания.** Поле `type` исключено из
формы изменения (**ПРОВЕРЕНО**:
`packages/twenty-server/src/engine/metadata-modules/field-metadata/dtos/update-field.input.ts:22-33`).
Ошиблись типом — поле удаляется вместе с колонкой и всеми данными, и заводится
заново. У нас одиннадцать сущностей и около двухсот полей. Одна невнимательная
минута здесь стоит потерянных сумм по договорам или потерянных пробегов.

Поэтому: сначала бумага, потом мышка.

# Часть 1. Девять правил, действующих на все объекты

## Правило 1. Объекты описываются кодом, а не мышкой

**Решение: все объекты заводятся описанием в коде приложения («манифестом»),
интерфейс используется только для представлений и мелочей показа.**

Почему без вариантов:

- **ПРОВЕРЕНО.** Составной уникальный признак (уникальна пара полей, а не одно)
  создаётся только из описания в коде:
  `packages/twenty-server/src/engine/core-modules/application/application-manifest/converters/from-index-manifest-to-universal-flat-index.util.ts:131`
  берёт `isUnique` из описания. В пути «мышкой» и «через программный интерфейс»
  этот признак жёстко зашит в «нет»:
  `packages/twenty-server/src/engine/metadata-modules/index-metadata/services/index-metadata.service.ts:196,245`.
  Без составного уникального признака **не работает защита от дублей при
  повторном переносе из старой базы** (правило 8 ниже).
- **ПРОВЕРЕНО.** Заведённый мышкой объект получает лишнюю текстовую колонку
  `name` (заголовок записи) автоматически:
  `packages/twenty-server/src/engine/metadata-modules/flat-object-metadata/utils/from-create-object-input-to-flat-object-metadata-and-flat-field-metadatas-to-create.util.ts:96`.
  При описании кодом эта колонка **не добавляется** — заголовком назначается
  любое наше поле (`labelIdentifierFieldMetadataUniversalIdentifier` в
  `packages/twenty-shared/src/application/objectManifestType.ts`). Это важно:
  колонку-заголовок нельзя спрятать правами (см. правило 7).
- **ПРОВЕРЕНО.** Только из описания в коде можно сразу задать показ денег
  «полностью, два знака» и запрет на правку поля с экрана
  (`universalSettings`, `isUIEditable` —
  `packages/twenty-shared/src/application/fieldManifestType.ts`).

**Цена этого решения, и её надо знать.** При выкладке приложения включён режим
«чего нет в описании — того нет и в базе»: `inferDeletionFromMissingEntities: true`
(**ПРОВЕРЕНО**, `.../application-manifest/application-manifest-migration.service.ts:214`).
Убрали объект из описания и выложили — **таблица удаляется вместе с данными.**
Отсюда обязательный порядок работ, а не пожелание: снимок базы → предварительный
просмотр (`dryRun`) → выкладка.

## Правило 2. Что появляется у каждого объекта само

**ПРОВЕРЕНО на живой базе** (`psql -d default`, таблица `_pet` в схеме рабочей
области — настоящий свой объект): к нашим полям Twenty сам добавляет

| Колонка | Что это |
|---|---|
| `id` | уникальный ключ записи, UUID, ставится сам |
| `createdAt`, `updatedAt` | когда создана и изменена, с часовым поясом |
| `createdBySource/Name/WorkspaceMemberId/Context`, `updatedBy…` | кто и откуда создал и менял (по четыре колонки на каждое) |
| `deletedAt` | «в корзине» — пусто, пока запись жива |
| `position` | место в ручной сортировке |
| `searchVector` | указатель для поиска |

**Следствие 1.** Поля «создана», «создан», «кем заведён», «когда заведён» из
описи **заводить своими полями не нужно** — они уже есть. Исключение: если в
старой базе автор указан текстом (фамилия, а не пользователь Twenty), то при
переносе его некуда положить, и тогда нужно своё текстовое поле «Заведено (из
старой базы)».

**Следствие 2, неприятное.** Поиск строится с настройкой `simple`, то есть без
русской морфологии (**ПРОВЕРЕНО**, видно прямо в определении колонки:
`to_tsvector('simple', …)`). «Путевого» не найдёт «путевой». Людей надо
предупредить, иначе они решат, что поиск сломан.

## Правило 3. «Обязательное поле» в Twenty означает не то, что вы думаете

**ПРОВЕРЕНО.** Признак «поле не может быть пустым» (`isNullable: false`)
принимается только вместе со значением по умолчанию:
`packages/twenty-server/src/engine/workspace-manager/workspace-migration/workspace-migration-builder/validators/services/flat-field-metadata-validator.service.ts:194-204`
(«Default value cannot be null for non-nullable fields»).

**По-человечески:** база может гарантировать, что в поле что-то лежит, но не
может гарантировать, что человек это заполнил. Поставили «обязательно» — придётся
задать значение-заглушку (пустая строка, ноль), и запись с заглушкой пройдёт как
заполненная.

**ПРОВЕРЕНО, и это ещё важнее.** Колонка-ссылка на другой объект **всегда**
создаётся допускающей пустоту — признак зашит:
`.../workspace-migration-runner/utils/generate-column-definitions.util.ts:134`
(`isNullable: true` прямо в описании колонки-ссылки, без всяких условий). То есть
«у рейса обязательно должна быть машина» базой не выражается вообще.

**ПРОВЕРЕНО.** Денежное поле тоже нельзя сделать обязательным: подполя суммы
помечены необязательными (`currency.composite-type.ts:4-20`), а колонка
составного поля допускает пустоту, если подполе необязательно —
`generate-column-definitions.util.ts:90-91`.

**Решение.** В плане ниже колонка «Обязательность» означает три разные вещи, и
они помечены разными словами:

| Пометка | Что реально стоит за ней |
|---|---|
| **база** | `isNullable: false` + значение по умолчанию. База не даст записать пусто |
| **правило** | Проверяет наша служба документов при записи и форма при вводе. База допускает пусто |
| **нет** | Может быть пустым, и это нормально |

Пометка «правило» — не слабость плана, а честное описание: **в Twenty
обязательность заполнения живёт не в схеме, а в том, кто пишет данные.** Наша
служба документов — единственная дверь, через которую приходят суммы и
документы, значит проверка встаёт там (см. [DOCS_SERVICE_CONTRACT](../architecture/DOCS_SERVICE_CONTRACT.md)).

## Правило 4. Уникальность и обязательность несовместимы

**ПРОВЕРЕНО, и это неочевидно.** Уникальный признак нельзя поставить на поле, у
которого есть значение по умолчанию:
`.../workspace-migration-builder/validators/services/flat-index-metadata-validator.service.ts:160-181`
(«Unique index cannot be created for field … of type …», условие
`!isDefined(defaultValue)`).

А из правила 3: обязательность **требует** значения по умолчанию.

**Значит: поле не может быть одновременно уникальным и обязательным на уровне
базы.** Для нас это оказывается кстати: номер путевого листа обязан быть пустым
у черновика (см. решение 2). Но для «Позывного» машины и «Наименования»
контрагента это означает — уникальность база держит, обязательность держим мы.

Ещё две проверенные мелочи про уникальность:

- **ПРОВЕРЕНО.** Уникальность нельзя ставить на ссылки (кроме случая ниже), на
  файлы и на деньги: `packages/twenty-front/src/modules/settings/data-model/fields/forms/utils/canBeUnique.ts:6-20`
  плюс отсутствие признака `isIncludedInUniqueConstraint` у подполей денег.
- **ПРОВЕРЕНО.** А вот в составной уникальный признак **ссылку включить
  можно**, если это ссылка «многие-к-одному» — она держит одну колонку, и база
  её проиндексирует: `flat-index-metadata-validator.service.ts:193-205` с
  пояснением прямо в комментарии кода. Этим мы делаем связь «один-к-одному»
  (нужно для персональных данных водителя).
- **ПРОВЕРЕНО.** Предел — 10 своих указателей на объект:
  `packages/twenty-shared/src/constants/MaxCustomIndexesPerObject.ts:1`. У нас
  на самый нагруженный объект выходит четыре. Запас есть.

## Правило 5. У каждой связи обязательно указывать, что делать при удалении

**ПРОВЕРЕНО, и это ловушка, которая молча уносит данные.** При создании связи
внешний ключ получает поведение из настроек поля, а **если настройка не
указана — подставляется «удалить по цепочке»**:

```
// packages/twenty-server/src/engine/workspace-manager/workspace-migration/
// workspace-migration-runner/action-handlers/field/services/
// create-field-action-handler.service.ts:243-246
onDelete: convertOnDeleteActionToOnDelete(flatFieldMetadata.settings?.onDelete)
          ?? 'CASCADE',
```

Путь «мышкой» настройку проставляет сам («обнулить ссылку» —
`.../flat-field-metadata/utils/generate-morph-or-relation-flat-field-metadata-pair.util.ts:36`),
а описание в коде передаёт настройки как есть, ничего не подставляя
(**ПРОВЕРЕНО**, `.../converters/from-field-manifest-to-universal-flat-field-metadata.util.ts:90`
— `universalSettings: fieldManifest.universalSettings ?? null`).

**По-человечески:** мы выбрали описывать объекты кодом (правило 1), и значит
забытая строчка в описании связи «машина → рейсы» превращает окончательное
удаление одной машины в исчезновение всех её рейсов.

**Решение.** В плане у каждой связи указано поведение явно, из четырёх
возможных (**ПРОВЕРЕНО**, `packages/twenty-shared/src/types/RelationOnDeleteAction.type.ts`):

| Мы пишем | Что делает база |
|---|---|
| «обнулить» | ссылка стирается, запись остаётся (рейс без машины) |
| «запретить» | база не даст удалить, пока есть ссылающиеся записи |
| «по цепочке» | удаляет связанные записи. **У нас не используется нигде** |

Наш выбор по умолчанию — **«запретить»** для всего, что попадает в сданные
документы (машина, водитель, контрагент), и «обнулить» для справочного
(точка, прицеп). Это ровно то же правило, что уже действует в старой базе:
водитель с выписанными листами не удаляется, а помечается неактивным.

## Правило 6. Деньги — только тип «Деньги», и только через нашу службу

Полный разбор — в решении 1. Коротко: тип «Деньги», единица хранения
**микро-рубль** (одна миллионная рубля), копейка = 10 000 микро-рублей, запись
только целым числом через программный интерфейс.

## Правило 7. Что можно спрятать правами, а что нельзя

**ПРОВЕРЕНО** (из [аудита, раздел 06](../architecture/audit/06-prava-i-bezopasnost.md),
перепроверено мной): запрет на поле работает в запросе к базе, а не в браузере —
`packages/twenty-server/src/engine/twenty-orm/repository/permissions.utils.ts:501-551`.
Запрос, где среди запрашиваемых колонок есть запрещённая, отклоняется целиком;
запрос «дай все поля» при наличии хоть одного запрета отклоняется тоже.

Но:

- **ПРОВЕРЕНО.** Запрет двоичный: роль видит поле везде (список, карточка,
  выгрузка в файл) или не видит нигде. Разделения «в списке нет, в карточке
  есть» **в коде не существует**.
- **ПРОВЕРЕНО.** Поле-заголовок записи запретить нельзя никогда
  (`workspace-roles-permissions-cache.service.ts:203-224` возвращает разрешение
  принудительно). Значит **в заголовок записи не должно попадать ничего
  чувствительного.**

Отсюда правило для плана: **что нельзя показывать — выносим в отдельный объект,
а не прячем полем.** Разбор — в решении 3.

## Правило 8. Внешний идентификатор — у всех одиннадцати

Два текстовых поля на каждом объекте плюс составной уникальный признак на их
пару. Разбор — в решении 4.

## Правило 9. Список выбора менять можно, тип — нельзя

**ПРОВЕРЕНО.** Значения списка выбора («Состояние»: в работе / завизирован / …)
после создания **изменяемы**: есть отдельная обработка последствий такого
изменения — `.../flat-field-metadata/utils/handle-enum-flat-field-metadata-update-side-effects.util.ts:36-78`
(пересчитываются отборы и колонки досок).

**ПРОВЕРЕНО, но с оговоркой.** В базе список выбора — это отдельный тип-перечень
PostgreSQL (видно на живой базе: колонка `species` имеет тип `_pet_species_enum`).
Изменение списка выполняется перестройкой колонки с переносом значений по карте
«старое → новое»
(`.../twenty-orm/workspace-schema-manager/services/workspace-schema-enum-manager.service.ts:146-240`).

**СЛЕДУЕТ ИЗ КОДА:** значение, которого нет в карте переноса (то есть удалённое
из списка), в новую колонку не попадает — **записи с этим значением его
теряют**. Правило: значения из списка не удалять, а помечать неиспользуемыми,
пока не убедились, что записей с ними нет.

# Часть 2. Одиннадцать объектов, поле за полем

## Как читать таблицы

- **Наше поле** — как в описи и как назовём человеку.
- **Тип Twenty** — точный тип поля, менять потом нельзя.
- **Обяз.** — база / правило / нет (см. правило 3).
- **Уник.** — держит ли база уникальность.
- **Примечание** — на что смотреть.

Техническое имя (то, что окажется именем колонки) Twenty выводит из названия
сам, транслитерацией. **ПРОВЕРЕНО запуском** настоящей функции
`computeMetadataNameFromLabel` из репозитория: «Путевой лист» → `putevoyList`,
«Норма расхода, сотые» → `normaRashodaSotye`, «Периодичность перезарядки, мес» →
`periodichnostPerezaryadkiMes`. Все имена читаемы и укладываются в предел 63
знака; ни одно не попадает в список из 63 запрещённых имён
(`packages/twenty-shared/src/metadata/constants/reserved-metadata-name-keywords.constant.ts`).
**Это закрывает открытый вопрос В3 аудита.** Технические имена всё равно задаём
в описании явно, чтобы они не менялись вслед за переименованием на экране.

Поля «создана / создан / когда заведён / кем заведён» в таблицах не повторяются:
они есть у всех объектов сами (правило 2).

## 1. Контрагент

Заголовок записи — **Наименование**.

| Наше поле | Тип Twenty | Обяз. | Уник. | Примечание |
|---|---|---|---|---|
| Наименование | Текст | правило | **да** | Уникальность базы — с учётом регистра, см. ниже |
| Наименование для сравнения | Текст | правило | **да** | Служебное: наименование в нижнем регистре без лишних пробелов. Пишет служба документов. Скрыто с экрана |
| Адрес | Текст | нет | нет | Одной строкой, как в старой базе. Готовый тип «Адрес» не берём — в нём восемь чужих полей и нет корпуса и квартиры |
| Телефон | Телефоны | нет | нет | Составной тип: номер + код страны + код вызова + дополнительные |
| ОКПО | Текст | нет | нет | Контрольная сумма — снаружи, см. ниже |
| ОГРН | Текст | нет | нет | То же |
| ИНН | Текст | нет | **да** | То же. Уникальность держит базу от двойного заведения |
| КПП | Текст | нет | нет | То же |
| Банк | Текст | нет | нет | |
| БИК | Текст | нет | нет | |
| Расчётный счёт | Текст | нет | нет | Проверяется только в паре с БИК |
| Корреспондентский счёт | Текст | нет | нет | |
| Основная организация | Да/Нет | база (по умолчанию «нет») | нет | «Наша организация» среди контрагентов |
| Система-источник | Текст | база | пара | См. решение 4 |
| Идентификатор в источнике | Текст | база | пара | См. решение 4 |

**Все реквизиты — текст, и это не лень.** **ПРОВЕРЕНО:** проверки формата на
вводе (маска, шаблон) в Twenty нет вовсе — проверяющий типы код
(`flat-field-metadata-type-validator.service.ts:57-84`) смотрит только на
внутреннюю согласованность описания поля, а не на содержимое. Число тут тоже не
годится: ИНН с ведущим нулём числом хранить нельзя. **Контрольные суммы ИНН, КПП,
ОГРН, ОКПО, БИК и согласованность счёта с БИК остаются в службе документов** —
ровно как записано в описи (пункт 8, ступень «3 + 8»).

**Уникальность наименования: Twenty её НЕ закрывает, и это надо назвать вслух.**
**ПРОВЕРЕНО запуском на нашей PostgreSQL 18.4:** обычный уникальный указатель
считает «ООО ПожСервис» и «ООО ПОЖСЕРВИС» разными строками — обе записались.
В старой базе для этого заведено своё правило сравнения (`NOCASE_UNICODE`), в
Twenty такого переключателя нет.

**Решение:** второе поле «Наименование для сравнения» — то же наименование,
приведённое к нижнему регистру и без двойных пробелов, уникальное. Заполняет
служба документов при записи. **ПРОВЕРЕНО там же:** `lower()` в PostgreSQL с
русскими буквами работает правильно — `lower('ООО ПОЖСЕРВИС') = lower('ООО ПожСервис')`
даёт «истина». Цена — одна лишняя колонка и обязанность службы её заполнять;
выигрыш — двойник не заводится, и это проверяет база, а не добрая воля.

## 2. Машина

Заголовок записи — **Позывной**.

| Наше поле | Тип Twenty | Обяз. | Уник. | Примечание |

**Почему целые числа, а не дробные, и что даёт Twenty.**

**ПРОВЕРЕНО на живой базе:** тип «Число» превращается в колонку `double precision`
— число с плавающей запятой. Целые числа такая колонка хранит **точно** до
9 007 199 254 740 992 (девять квадриллионов). Пробег в метрах, бак в миллилитрах и
норма в сотых долях в этот запас укладываются с огромным перевесом, и накопление
погрешности, которого мы боялись, здесь не возникает — оно возникает только у
дробных значений.

**ПРОВЕРЕНО, и это лучше, чем считалось в аудите.** Настройка «целое / большое
целое» у поля-числа **не декоративная**: она меняет тип значения в программном
интерфейсе (`.../workspace-schema-builder/utils/get-number-scalar-type.util.ts`
и `.../services/type-mapper.service.ts:140-147`). При настройке «целое» интерфейс
принимает только целые и отвергает дробное на входе. Тип колонки при этом
остаётся дробным — то есть это **проверка на входе, а не гарантия базы**, но
проверка настоящая.

Оговорка: «целое» в программном интерфейсе — это тридцатидвухразрядное целое,
предел 2 147 483 647. Для пробега в метрах это 2,1 млн км — близко к пределу для
грузовика за весь срок службы, поэтому **пробег берём «большое целое»**, всё
остальное — «целое».

# Часть 3. Решения и почему

## Решение 1. Деньги: тип «Деньги», запись только целым числом, показ настраивается в коде

### Что проверено

**ПРОВЕРЕНО. Хранение точное.** Тип «Деньги» — составной, из двух частей:
`amountMicros` (число типа NUMERIC — точное десятичное, без плавающей запятой) и
`currencyCode` (текст). `packages/twenty-shared/src/types/composite-types/currency.composite-type.ts:4-20`.
**ПРОВЕРЕНО на живой базе:** колонка `…AmountMicros` действительно имеет тип
`numeric`.

Единица хранения — **микро-рубль**, одна миллионная рубля. **Копейка = 10 000
микро-рублей.** Пересчёт копеек в микро-рубли — умножение целого на целое, то
есть точный.

**ПРОВЕРЕНО. Обычное «Число» для денег брать нельзя.** Тип «Число» превращается
в колонку `double precision` — число с плавающей запятой
(`.../workspace-migration-runner/utils/field-metadata-type-to-column-type.util.ts:25-27`,
подтверждено на живой базе). Настройка «целое» тип колонки не меняет.

**ПРОВЕРЕНО. Взять точный тип NUMERIC напрямую тоже нельзя** — он запрещён к
созданию пользователем, с сообщением «Field type NUMERIC is not supported. Use
Number instead»
(`.../flat-field-metadata/services/flat-field-metadata-type-validator.service.ts:69-73`).

**Вывод: точных способов ровно один — тип «Деньги».**

### Что с копейками на самом деле

**ПРОВЕРЕНО (из аудита, раздел 01, с запуском).** Когда сумму набирают в поле на
экране, она умножается на миллион обычной дробной арифметикой
(`packages/twenty-front/src/utils/convertCurrencyToCurrencyMicros.ts:4`), и 8,11 ₽
превращается в 8 109 999,999999999 микро-рубля вместо 8 110 000. При чтении
дробный хвост отбрасывается
(`.../twenty-orm/utils/format-composite-field-value.util.ts:13-16`). Потеря —
доли копейки, но она **есть**, и это ровно тот класс дефектов, который у нас
ловился тестами на настоящих реквизитах.

### Что делаем

**1. Суммы приходят готовым целым числом микро-рублей через программный
интерфейс** — из службы документов. Путь с умножением на миллион не
задействуется вовсе. Это не новое требование, а та же граница, которую провёл
ADR-001; здесь она подтверждается фактом из кода, а не удобством.

**2. Правку денежных полей с экрана выключаем в описании объекта.**
**ПРОВЕРЕНО:** признак `isUIEditable: false` у поля делает его на экране
доступным только для чтения —
`packages/twenty-front/src/modules/object-record/read-only/utils/isRecordFieldReadOnly.ts:50-56`.
**ПРОВЕРЕНО и это ограничение:** признак действует только в браузере, на сервере
проверки нет (искал в `engine/api` и `engine/twenty-orm` — совпадений нет). То
есть это **защита от случайности, а не запрет.**

**3. Настоящий запрет — правом на поле.** Роль, у которой
`canUpdateFieldValue = false` на денежном поле, не запишет в него ничего: проверка
идёт в запросе к базе (`.../twenty-orm/repository/permissions.utils.ts`,
проверка изменяемых колонок). Право снимается со всех ролей, кроме той, под
которой ходит служба документов.

**4. Показ настраивается один раз в коде, а не мышкой у каждого поля.**
**ПРОВЕРЕНО:** у денежного поля есть настройки `format` («сокращённо» /
«полностью») и `decimals` (знаков после запятой)
(`packages/twenty-shared/src/types/FieldMetadataSettings.ts`, разделы
`FieldMetadataCurrencySettings`), и описание объекта передаёт их как есть
(`.../converters/from-field-manifest-to-universal-flat-field-metadata.util.ts:90`).
По умолчанию стоит «сокращённо» и ноль знаков — бухгалтер увидит «1,2k» вместо
«1 234,56 ₽». **В описании каждого денежного поля пишем `format: полностью,
decimals: 2`.** Это снимает риск Р1 из аудита целиком, а не «контрольным
списком».

**5. Валюта.** Подполе «код валюты» — отдельная текстовая колонка, необязательная.
Ставим значением по умолчанию рубль (рубль в справочнике валют есть —
`packages/twenty-shared/src/constants/CurrencyCode.ts`). Пустой код валюты в
записи означал бы сумму без единицы измерения.

**6. Чего нельзя сделать, и это не лечится.** Денежное поле **невозможно**
сделать обязательным на уровне базы (правило 3) и **невозможно** сделать
уникальным (правило 4). Обе вещи нам не нужны, но знать об этом надо, чтобы не
пытаться.

## Решение 2. Номер путевого листа: черновик без номера, номер при выписке, удаление выключено

### Что нужно и чего в Twenty нет

Нужно: номер уникален **среди выписанных**; черновики номеров не занимают;
счётчик только растёт, чтобы удалённая пачка не отдала свои номера повторно.

**ПРОВЕРЕНО. Частичного уникального признака («уникален там, где выполняется
условие») в Twenty нет, и обойти это настройкой нельзя.** Условие берётся из
белого списка ровно из одного разрешённого значения:

```
// packages/twenty-server/src/engine/workspace-manager/workspace-migration/
// utils/validate-index-where-clause.util.ts:1-3
const ALLOWED_INDEX_WHERE_CLAUSES = new Set(['"deletedAt" IS NULL']);
```

**ПРОВЕРЕНО, и это строже, чем считалось в аудите.** Даже это единственное
разрешённое условие нашим объектам недоступно: во всех трёх путях создания
условие жёстко проставлено пустым — мышкой и через интерфейс
(`.../flat-field-metadata/utils/generate-index-for-flat-field-metadata.util.ts:38`),
из описания в коде
(`.../converters/from-index-manifest-to-universal-flat-index.util.ts:129`).
Разрешённое условие используют только собственные объекты Twenty (почтовые
папки и переписка). **Само поле условия намеренно не выведено наружу** — об этом
есть комментарий в коде (`.../index-metadata/dtos/create-index.input.ts:36-37`).

### Что работает вместо этого

**Пустое значение уникальности не мешает.** PostgreSQL в обычном уникальном
указателе считает пустые значения различными, и Twenty создаёт именно обычный
указатель, без оговорки «считать пустые одинаковыми»
(**ПРОВЕРЕНО**, `.../workspace-schema-manager/services/workspace-schema-index-manager.service.ts:56-77`).

**ПРОВЕРЕНО запуском на нашей PostgreSQL 18.4** — не рассуждением, а опытом:

| Что сделали | Что ответила база |
|---|---|
| завели три черновика без номера | все три записались |
| выписали № 4417 | записался |
| попытались выписать № 4417 второй раз | **отказ**, «нарушение уникальности» |
| отправили № 4417 в корзину и завели заново | **отказ** — номер занят записью в корзине |

Первые три строки — это ровно то, что нам нужно, и держит это база, а не
проверка в коде, которую можно обойти импортом или ошибкой.

**Порядок работы меняется, и секретаря надо предупредить:** номер перестаёт
вводиться заранее. Черновик живёт без номера, номер присваивается в момент
выписки. Чтобы черновик было видно в списке, заголовком записи служит не номер,
а поле «Обозначение».

### Четвёртая строка таблицы — это не дефект, а нужное нам поведение

Удалённая запись держит свой номер занятым, пока лежит в корзине (по умолчанию
14 дней — **ПРОВЕРЕНО**,
`.../legacy-typeorm-migrations-do-not-add/common/1760356369619-add-workspace-trash-retention.ts:8`).
Аудит назвал это ловушкой. **Для путевого листа это правильное поведение:
выписанный номер не должен переиспользоваться никогда** — повтор номера делает
документ недействительным.

Поэтому решение не «обойти», а **закрепить**:

1. **Удаление путевых листов выключено для всех ролей** — признаками
   `canSoftDeleteObjectRecords` и `canDestroyObjectRecords`
   (`.../object-permission/object-permission.entity.ts:51-60`). **ПРОВЕРЕНО, и
   это важно: запрет на объекте перекрывает общее разрешение роли.** Разбор прав
   идёт так: сначала берётся признак роли «может удалять всё», затем поверх него
   накладывается признак на конкретный объект, и он побеждает
   (`.../role/services/workspace-roles-permissions-cache.service.ts:175-201`,
   `objectRecordPermissionsOverride?.canSoftDeleteObjectRecords ?? canSoftDelete`).
   То есть даже администратор, которому разрешено удалять всё, путевой лист не
   удалит. Ошиблись — не удаляют, а **аннулируют**: состояние «аннулирован»,
   дата и причина. Номер остаётся занятым навсегда, как и положено бланку
   строгой отчётности.
2. **Ловушка «номер занят невидимой записью» при этом исчезает сама** — в
   корзине путевых листов просто не бывает.
3. Правку исходников Twenty, чтобы разрешить условие «кроме корзины», мы
   **сознательно не делаем**: она вернула бы возможность переиспользовать номер
   удалённого листа, то есть починила бы то, что нам ломать не надо. (Технически
   такая правка мала — передать условие из описания в уже существующую проверку
   — и её стоит держать в уме для других объектов, если когда-нибудь
   понадобится.)

### Счётчик, который только растёт

Отдельный объект «Счётчик номеров» с полями «Ключ счётчика» и «Последний
выданный номер». Почему не «максимум из выписанных»: это уже ловилось тестом в
старом приложении — по максимуму удалённая пачка отдала бы свои номера повторно.

**ПРОВЕРЕНО от противного:** среди 23 типов полей
(`packages/twenty-shared/src/types/FieldMetadataType.ts`) типа
«самовозрастающий номер» нет. Счётчик — наш объект, увеличивает его служба
документов при выписке.

**Двойная защита.** Если два человека выпишут лист одновременно и счётчик отдаст
один номер дважды, **база откажет второму** — уникальность номера этого не
допустит, и служба переспросит счётчик. То есть счётчик отвечает за «только
растёт», а база — за «не повторяется». Ни одно из двух правил не держится на
одной лишь аккуратности кода.

## Решение 3. СНИЛС и номер удостоверения: отдельный объект, а не спрятанное поле

### Почему полем нельзя

**ПРОВЕРЕНО.** Право на отдельное поле в Twenty есть и работает в базе, а не в
браузере (правило 7). Но оно двоичное: **разделения «в списке не отдавать, в
карточке отдавать» в коде нет вовсе.** Кто видит СНИЛС в карточке — получит его
и списком на всех водителей, и выгрузкой в файл.

**ПРОВЕРЕНО, и это добивает вариант «спрятать колонку из представления»:**
сотрудник без всяких прав может создать своё личное представление и вернуть
колонку (`.../view-permissions/services/view-access.service.ts:122-128`
разрешает менять свои неопубликованные представления без права). **Скрытая
колонка — удобство, а не защита.**

В старом приложении разделение сделано отдельным запросом специально. В Twenty
такого рычага нет.

### Что делаем

**Отдельный объект «Персональные данные водителя»**, связанный с водителем
один-к-одному (объект 4 в части 2). Тогда:

- список водителей **физически не содержит** этих колонок — их неоткуда взять;
- доступ закрывается правом на объект (`canReadObjectRecords`), а не на поле, и
  действует во всех интерфейсах сразу, включая выгрузку;
- выгрузка списка водителей в файл безопасна по построению, а не по настройке.

Связь «один-к-одному» делается ссылкой «многие-к-одному» из персональных данных
на водителя плюс уникальный признак на эту ссылку — **ПРОВЕРЕНО**, что ссылку в
уникальный признак включать можно, если это ссылка «многие-к-одному»
(правило 4).

Заголовок записи — нейтральная метка, **не ФИО и не СНИЛС**: поле-заголовок
правами не закрывается ни от кого (правило 7).

Цена: лишний переход из карточки водителя в связанную запись. Это дёшево.

### Чего это решение НЕ закрывает — и это надо решить отдельно

**ПРОВЕРЕНО, и это дыра.** История изменений записи (кто что менял) хранит
«было / стало» по каждому изменённому полю
(`packages/twenty-server/src/modules/timeline/services/timeline-activity.service.ts:137-151`),
и **включена она у наших объектов принудительно**: в описании объекта признак
«вести историю» жёстко проставлен «да»
(`.../converters/from-object-manifest-to-universal-flat-object-metadata.util.ts:33`,
`isAuditLogged: true`), в описании его выключить нечем. Гасит запись истории
именно этот признак
(`.../workspace-query-runner/listeners/entity-events-to-db.listener.ts:81,110`).

**По-человечески:** СНИЛС не виден в карточке, но виден в истории её изменений.

Три возможных ответа, в порядке предпочтения:

1. **Правка форка — самая маленькая из возможных.** Добавить признак «вести
   историю» в описание объекта и передавать его вместо жёсткого «да» (одна
   строка в одном файле-переходнике плюс поле в описании типа). Для объекта
   «Персональные данные водителя» ставим «нет». **Требуется проверить**, что
   выключение не ломает ничего смежного, — этого я не проверял.
2. Закрыть доступ к самой истории изменений правами. **По аудиту (СЛЕДУЕТ ИЗ
   КОДА) — не выйдет:** история это системный объект, права на него не
   проверяются.
3. Ничего не делать и записать это как принятый остаточный риск в согласии с
   владельцем.

**Отдельно и честно:** кто открывал карточку и смотрел СНИЛС, не фиксируется
нигде и ни в каком виде — записи о чтении в Twenty нет (**ПРОВЕРЕНО** в аудите
раздела 06). Для персональных данных это существенный пробел, и его нельзя
закрыть настройкой.

## Решение 4. Внешний идентификатор: два поля и уникальность на их пару

### Зачем

Чтобы повторная выгрузка из старой базы не заводила те же машины и договоры
заново.

**ПРОВЕРЕНО.** Готового поля «откуда пришла запись» в Twenty нет — поиск по
`externalId` / `sourceRecordId` / `sourceSystem` по всему движку даёт совпадения
только внутри почтовых папок.

### Что делаем

Два текстовых поля на **каждом** из одиннадцати объектов:

| Поле | Тип | Что внутри |
|---|---|---|
| Система-источник | Текст | «pozhservis-sqlite» — откуда пришло |
| Идентификатор в источнике | Текст | ключ записи в старой базе, как есть |

Плюс **составной уникальный признак на пару этих полей** — именно он заставляет
механизм «обновить, если есть; создать, если нет» работать.

**ПРОВЕРЕНО, что механизм встроенный:**

- команда создания записей принимает признак «обновить, если есть»
  (`packages/twenty-server/src/engine/api/common/types/common-query-args.type.ts:58,63`);
- совпадение ищется по ключу записи **и по каждому уникальному признаку
  объекта, включая составные**
  (`.../common-create-many-query-runner/utils/get-conflicting-fields.util.ts:125-170`);
- найденные обновляются, ненайденные создаются
  (`.../common-create-many-query-runner.service.ts:275-283`).

Работает во всех трёх путях: программный интерфейс GraphQL (`upsert: true`),
программный интерфейс REST (`?upsert=true`), загрузка таблицы через экран
(включено всегда).

Текст, а не число: ключи в старой базе целые, но текст переживёт смену типа
ключа и не потеряет ведущие нули. Тип UUID тоже не годится — старые ключи не
UUID.

### Три вещи, о которых должен знать тот, кто пишет перенос

1. **ПРОВЕРЕНО.** За один вызов — не больше **200 записей**
   (`packages/twenty-shared/src/constants/QueryMaxRecords.ts:1`). Перенос 5 000
   машин — 25 вызовов.
2. **ПРОВЕРЕНО (из аудита).** Повторная выгрузка **воскрешает удалённые
   записи**: совпадения ищутся с учётом корзины, а при обновлении признак
   удаления снимается. Запись, которую бухгалтер удалил намеренно, вернётся
   после ночной выгрузки. Либо переносим это осознанно, либо перенос должен
   уважать удаление в Twenty. **Решить до первого повторного переноса.**
3. **ПРОВЕРЕНО (из аудита).** Встроенный поиск дублей и слияние записей для
   наших объектов **не заработают** — признак, по которому они включаются, у
   своих объектов всегда пуст. Дедупликация записей остаётся за службой
   документов, как и записано в описи (пункт 12).

**Расход указателей:** пара внешнего идентификатора — один составной признак.
Плюс по одному на каждое уникальное поле. Больше всего выходит у контрагента:
наименование, наименование для сравнения, ИНН, пара источника — четыре из
десяти. Запас есть.

## Решение 5. Где связь, где список выбора, где просто текст

Правило, по которому расставлены типы во всех таблицах выше:

| Берём | Когда | Примеры из нашей модели |
|---|---|---|
| **Ссылка на другой объект** | У значения есть своя карточка и своя жизнь: адрес, реквизиты, история, права | Организация, Машина, Водитель, Точка, Прицеп, Путевой лист, Контрагент |
| **Выбор из списка** | Значений мало, список закрытый и меняется раз в год; по значению нужны цветные метки, отбор и колонки на доске | Состояние, Тип топлива, Категория, Периодичность, Вид документа, Источник записи, Форма листа |
| **Список значений** | Несколько простых значений в одном поле, своей карточки у них нет | Категории у водителя (B, C, E) |
| **Текст** | Всё остальное. В том числе то, что похоже на число, но числом не является | ИНН, ОГРН, БИК, счета, номера, коды из старой системы |

Три пояснения к правилу.

**Почему реквизиты — текст, а не число.** ИНН с ведущим нулём числом не хранится,
а арифметики над ИНН не бывает. Заодно поле остаётся уникальным (правило 4 —
уникальность требует отсутствия значения по умолчанию, у текста это соблюдается
естественно).

**Почему «Состояние» — список, а не отдельный справочник-объект.** Переходы
между состояниями всё равно стережёт процесс, а не схема; отдельный объект дал бы
лишнюю таблицу, лишний переход и ничего сверх. Список выбора при этом изменяем
(правило 9) — с одной оговоркой: **значение из списка не удалять, а помечать
неиспользуемым**, иначе записи с ним потеряют значение при перестройке колонки.

**Почему «Справочник» и «Поле-дата» в правиле срока — текст.** Ссылаться из
записей на описание объектов и полей нельзя: описание живёт в другой схеме базы.
Это единственное место в плане, где мы сознательно берём хрупкое решение, и
мера против него — сверка перечня правил с перечнем полей после каждого
обновления Twenty.

---

# Часть 4. Контрольный список перед первой выкладкой

1. Перечень полей путевого листа (98), рейса (27) и машины (25) снят из
   работающей базы построчно и дописан в этот документ.
2. У **каждой** связи в описании явно указано поведение при удалении. Ни одной
   связи без этой строчки (иначе база получит «удалять по цепочке» — правило 5).
3. У **каждого** денежного поля в описании стоит «показывать полностью» и «два
   знака после запятой».
4. У каждого денежного поля выключена правка с экрана, и право на изменение
   снято со всех ролей, кроме служебной.
5. У всех одиннадцати объектов есть пара «Система-источник + Идентификатор в
   источнике» и составной уникальный признак на неё.
6. У объектов «Путевой лист» и «Водитель» выключено удаление для всех ролей.
7. Заголовок записи у «Персональных данных водителя» — нейтральная метка.
8. Выкладка идёт: снимок базы → предварительный просмотр → выкладка → сверка
   количества записей по каждому объекту.
9. На тестовой установке проверено: русские названия дают ожидаемые технические
   имена (уже проверено запуском, но подтвердить на живой выкладке), показ
   связки «лист ↔ прицепы» под бета-признаком выглядит приемлемо.

# Часть 5. Риски этого плана

**Р1. Забытая строчка в описании связи уносит данные.** Без явного указания
поведения при удалении база получает «удалять по цепочке», и окончательное
удаление машины уносит её рейсы. Мера: пункт 2 контрольного списка плюс отдельная
проверка перечня внешних ключей в базе после первой выкладки — глазами, один раз.

**Р2. Объект пропал из описания — таблица удалена вместе с данными.** Режим
«чего нет в описании, того нет и в базе» включён всегда. Мера: снимок базы перед
каждой выкладкой, обязательный предварительный просмотр, запрет выкладки в
рабочую систему из-под руки.

**Р3. Обязательность, которая держится на нас, однажды не сработает.** Половина
пометок «обязательно» в этом плане — правило, а не база (правило 3), и держится
на том, что данные приходят через службу документов. Прямой вызов программного
интерфейса мимо службы обойдёт всё. Мера: право на запись выдаётся служебной
роли, обычные роли пишут только то, что можно писать с экрана.

**Р4. СНИЛС виден в истории изменений.** Разобрано в решении 3, требует
отдельного решения владельца.

**Р5. Значение убрали из списка выбора — записи его потеряли.** Мера: правило
«не удалять, а помечать неиспользуемым» плюс проверка «сколько записей с этим
значением» перед изменением списка.

**Р6. Переименовали поле — правило срока перестало работать молча.** Самый
опасный вид отказа: отчёт формируется, предупреждения не приходят. Мера: сверка
перечня правил с перечнем полей после каждого обновления.

---

# Часть 6. Что в этом плане не проверено

- **Как поведёт себя уникальность при загрузке 200 записей, среди которых две с
  одинаковым номером.** Разбор на «обновить» и «создать» найден, поведение при
  столкновении внутри одной пачки не прослежено. Для нас это реальный случай
  первой выгрузки. **Проверять опытом на тестовой установке.**
- **Можно ли выключить историю изменений для одного объекта, не сломав
  смежное** (решение 3, вариант 1).
- **Как выглядит связка «лист ↔ прицепы» под бета-признаком** на живом экране.
- **Пределы на количество своих объектов и полей.** Предел на указатели нашёл
  (10 на объект), на объекты и поля — не нашёл; возможно, его нет.
- **Точный вид записи значения по умолчанию для кода валюты** в описании объекта
  (текстовые значения по умолчанию Twenty хранит как выражения языка запросов).
  Уточняется при написании описания, на схему не влияет.
