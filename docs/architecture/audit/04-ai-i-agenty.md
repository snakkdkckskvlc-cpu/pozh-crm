# 04. Агенты и модели

**Область:** агентный движок Twenty — что это, годится ли нам, и на каких условиях.
**Репозиторий:** Twenty 0.2.1, коммит b5826b2d. Только чтение; ничего не запускалось.
**Дата:** 11.08.2026

Каждое утверждение помечено уровнем доверия:
**ПРОВЕРЕНО** — прочитан код, указаны файл и строки;
**СЛЕДУЕТ ИЗ КОДА** — вывод однозначен, но цепочка целиком не прослежена;
**ПРЕДПОЛОЖЕНИЕ** — не проверял.

---

## Ответ одной строкой

Агентный движок в Twenty есть, он взрослый, и права инструментов проверяются
**в коде**, а не только в тексте подсказки модели. Локальная модель через Ollama
подключается штатным механизмом «совместимый с OpenAI поставщик» — переписывать
ничего не нужно, но есть три места, где придётся вмешаться руками. Поиска по
документам (RAG) в Twenty нет вовсе — эта часть остаётся у нас. И есть два пути,
которыми агент обходит собственные ограничения: интерпретатор кода и логические
функции. Оба выключаемы, но по умолчанию про них никто не подумает.

---

## 1. Что такое агент в Twenty

**ПРОВЕРЕНО.** Агент — это строка в таблице `agent`, а не код.
`packages/twenty-server/src/engine/metadata-modules/ai/ai-agent/entities/agent.entity.ts:18-74`.
Поля:

| Поле | Что это |
|---|---|
| `name`, `label`, `icon`, `description` | имя и подпись для человека |
| `prompt` | текст инструкции модели — то, что раньше было бы «системным сообщением» |
| `modelId` | какая модель отвечает |
| `responseFormat` | `text` или `json` со схемой ответа |
| `modelConfiguration` | включён ли поиск в интернете и поиск в X (Twitter) |
| `evaluationInputs` | набор пробных вопросов для проверки качества |

**ПРОВЕРЕНО.** Списка инструментов у агента **нет**. Что агенту разрешено — целиком
определяется его ролью. Роль привязывается отдельной записью `roleTarget`
(`ai-agent-role/ai-agent-role.service.ts:30-57`), и роль обязана быть помечена
«может назначаться агентам», иначе привязка отклоняется (`:145-150`).
Создать агента через интерфейс можно с полями label, prompt, modelId, roleId,
responseFormat, modelConfiguration — `ai-agent/dtos/create-agent.input.ts:23-87`.

**ПРОВЕРЕНО.** Агента можно описать и в коде приложения, декларативно:
`packages/twenty-sdk/src/sdk/define/agents/define-agent.ts:8-44`. Живой пример —
`packages/twenty-apps/examples/document-generator/src/agents/document-assistant.agent.ts`:
это те же самые поля, только в файле, который приезжает вместе с приложением.
**Для нас это важно:** нашего «помощника по документам» можно поставлять как часть
приложения, а не заводить руками в каждой установке.

**ПРОВЕРЕНО.** Запустить агента можно тремя способами, и они ведут себя по-разному:

1. **Чат** — `metadata-modules/ai/ai-chat/`. Собеседник видит поток ответа,
   переписка сохраняется.
2. **Шаг рабочего процесса** — `modules/workflow/workflow-executor/workflow-actions/ai-agent/ai-agent.workflow-action.ts:39-119`.
   Агент получает один текст-задание, отдаёт результат следующему шагу.
3. **Программный вызов `runAgent`** — `ai-agent-execution/services/agent-run.service.ts:46-161`.
   Из приложения или логической функции.

**ПРОВЕРЕНО.** Сам цикл «модель подумала → вызвала инструмент → получила результат →
подумала снова» реализован на библиотеке Vercel AI SDK (`generateText`) —
`ai-agent-execution/services/agent-async-executor.service.ts:377-468`.
Потолок — **300 шагов за один запуск** (`ai-agent/constants/agent-config.const.ts:2`).
Это очень много: один неудачный запуск может стоить заметных денег, если модель
платная, и заметного времени, если модель наша.

## 2. Инструменты: как объявлены, что на входе и что на выходе

**ПРОВЕРЕНО.** Инструмент — это объект из четырёх частей
(`engine/core-modules/tool/types/tool.type.ts:8-13`):

- `description` — текстовое описание для модели;
- `inputSchema` — **строгая схема входа** (Zod, преобразуется в JSON Schema);
- `execute(вход, контекст)` — сама работа;
- `flag` — необязательное требование к роли.

**ПРОВЕРЕНО.** Схемы **выхода нет**. `ToolOutput`
(`engine/core-modules/tool/types/tool-output.type.ts:3-13`) — это всегда
`{ success, message, error?, result?, warnings?, ... }`, где `result` — что угодно.
То есть вход проверяется машиной, а выход — на совести автора инструмента.
Для нас это значит: если наш сервис документов вернёт не то, никто этого не заметит,
кроме модели, которая просто соврёт красиво.

**ПРОВЕРЕНО.** Инструменты не пишутся по одному, а **порождаются** десятью
поставщиками по категориям (`twenty-shared/src/ai/constants/tool-category.const.ts`):
записи (CRUD), действия, рабочие процессы, метаданные, представления, дашборды,
меню, вебхуки, логические функции, роли.

**ПРОВЕРЕНО.** Самое важное — записи. На каждый объект автоматически создаётся до
десяти инструментов (`tool-provider/providers/database-tool.provider.ts:128-450`):
`find_many_…`, `find_one_…`, `group_by_…`, `create_one_…`, `create_many_…`,
`update_one_…`, `update_many_…`, `upsert_many_…`, `delete_one_…`, `delete_many_…`.
Схема входа строится из настоящих полей объекта, с учётом закрытых для роли полей
(`restrictedFields`, `:167`). **Следствие для нас:** как только мы заведём объект
«Путевой лист», агент сразу умеет его искать, создавать и менять — писать код не нужно.

**ПРОВЕРЕНО.** Инструментов быстро становится сотни, поэтому есть два режима:

- **предзагрузка** — все схемы сразу, для узких задач в рабочих процессах
  (`agent-async-executor.service.ts:145-179`);
- **ленивый** — модели показывают только список имён и два мета-инструмента,
  `learn_tools` (узнать схему) и `execute_tool` (вызвать по имени)
  (`agent-async-executor.service.ts:185-250`).

**ПРОВЕРЕНО.** Ответ инструмента длиннее ~16 КБ не попадает в разговор целиком:
он «сливается» в файл, а модель ходит по нему отдельными инструментами
(`tool/tools/output-navigation-tool/constants/max-inline-tool-output-bytes.constant.ts:4`).
Это хорошая новость для наших таблиц на тысячи строк — разговор не распухнет.

## 3. Права инструментов: в коде или в инструкции?

Это главный вопрос раздела, и ответ хороший.

**ПРОВЕРЕНО. Права проверяются в коде, дважды.**

**Слой первый — что агент вообще видит.** Инструменты на запись создаются только
для тех объектов, где роль имеет соответствующее право:
`database-tool.provider.ts:141-149` читает `canReadObjectRecords`,
`canUpdateObjectRecords`, `canSoftDeleteObjectRecords`, и дальше
`:175, :262, :398` решают, порождать ли инструмент. Нет права — нет инструмента,
модель о нём просто не узнает.

**Слой второй — что произойдёт при вызове.** Даже если имя инструмента как-то
дошло до модели, при исполнении права передаются вниз:
`tool-provider/services/tool-executor.service.ts:101-243` передаёт
`rolePermissionConfig` в каждую операцию над записями. Дальше
`twenty-orm/entity-manager/workspace-entity-manager.ts:138-193` собирает набор
прав, а `twenty-orm/repository/permissions.utils.ts:94-160` бросает
«доступ запрещён» до того, как запрос уйдёт в базу. Проверяются не только объекты,
но и отдельные поля.

**ПРОВЕРЕНО.** Есть и приятная тонкость. Когда агент запускается «от имени
сотрудника», его права — это **пересечение** роли агента и роли сотрудника:
`ai-agent-execution/utils/build-agent-role-permission-config.util.ts:5-17`
(`intersectionOf`), а само пересечение считается в
`workspace-entity-manager.ts:172-181`. Проще говоря: агент никогда не может больше,
чем может человек, который его позвал, и никогда больше, чем разрешено самому агенту.
Если одну из ролей не удалось разрешить — доступ закрывается целиком (`:178-180`),
то есть при неясности система запрещает, а не разрешает. Это правильное поведение.

**ПРОВЕРЕНО.** Опасные действия закрыты отдельными флагами роли
(`tool-provider/providers/action-tool.provider.ts:84-204`):
`HTTP_REQUEST_TOOL` (запрос в сеть), `SEND_EMAIL_TOOL` (письма),
`CREATE_CALENDAR_EVENT_TOOL`, `CODE_INTERPRETER_TOOL` (выполнение кода).
Доступ к самому ИИ тоже флаг роли — `AI`
(`ai-chat/resolvers/agent-chat.resolver.ts:49`, `ai-agent-execution/resolvers/agent-run.resolver.ts:20`).

### Три места, где защита слабее, чем кажется

**ПРОВЕРЕНО. Первое: логические функции никак не ограничены ролью.**
`tool-provider/providers/logic-function-tool.provider.ts:46-107` — в этом методе
нет ни одного обращения к правам: **все** логические функции с настройкой
«вызывается как инструмент» становятся инструментами для любого, кто открыл чат.
И при исполнении `tool-executor.service.ts:283-307` вызывает функцию, передавая
только идентификатор рабочего пространства — ни роли, ни пользователя.
**Для нас это прямое следствие:** если мы выставим наш сервис документов как
логическую функцию, «Анализ договора» сможет запустить кто угодно, включая
секретаря, у которого нет прав на договоры.

**ПРОВЕРЕНО. Второе: часть действий выдаётся всем без флага.**
Там же, `action-tool.provider.ts:144-185`, безусловно добавляются
`search_help_center`, `navigate_app`, `extract_json_paths`, `search_output`,
`save_campaign`. Последний создаёт и правит черновики почтовых кампаний
(`modules/emailing/tools/save-campaign-tool.ts:16-50`); он проверяет права внутри
своего сервиса, но в каталоге виден всем.

**ПРОВЕРЕНО. Третье: системные объекты пропускаются мимо проверки.**
`twenty-orm/repository/permissions.utils.ts:120-124`: если объект помечен
системным (и это не «сотрудник»), проверка прав просто возвращается без решения.
В самом коде рядом стоит пометка авторов, что это надо улучшить. Наши собственные
объекты системными не будут, так что нас это касается косвенно.

**ПРОВЕРЕНО. Подтверждения человеком перед записью нет.** Поиск по словам
«approval», «confirmation», «human in the loop» во всём агентном коде даёт ровно
одно попадание — **текст в подсказке модели**
(`ai-chat/utils/build-workspace-setup-prompt-text.util.ts:57-59`: «ничего не
создавай, пока пользователь явно не одобрит»). Это пожелание, а не защита.
Никакого механизма «покажи и жди нажатия» в движке нет.

## 4. Поставщики моделей и Ollama

**ПРОВЕРЕНО.** Встроенный каталог — `ai-models/ai-providers.json`: OpenAI,
Anthropic, Google, Mistral, xAI. **Ollama в нём нет**; поиск слова «ollama» по
всему репозиторию не даёт ни одного совпадения.

**ПРОВЕРЕНО, и это ключевой факт.** Зато поддерживаются восемь «упаковок»
подключения (`twenty-shared/src/ai/constants/ai-sdk-packages.const.ts`), среди них
`@ai-sdk/openai-compatible` — «любой сервер, говорящий на языке OpenAI».
Сборка такого поставщика: `ai-models/services/sdk-provider-factory.service.ts:192-210`
— требуется только `baseUrl`. Ollama именно такой сервер (у него есть
OpenAI-совместимый вход `/v1`), поэтому подключение штатное, без правки ядра.

**ПРОВЕРЕНО.** Свои поставщики задаются переменной настройки `AI_PROVIDERS`
(`core-modules/twenty-config/config-variables.ts:1810-1816`, описание прямо говорит:
«для собственных адресов») и добавляются из панели администратора
(`core-modules/admin-panel/admin-panel.resolver.ts:571-589` — добавить поставщика,
`:621-656` — добавить модель). Настройки из `AI_PROVIDERS` накладываются поверх
встроенного каталога (`ai-models/services/provider-config.service.ts:24-32`).
Незнакомое имя поставщика по умолчанию считается OpenAI-совместимым
(`twenty-shared/src/ai/utils/infer-ai-sdk-package.util.ts:4-7`).

**ПРОВЕРЕНО. Загвоздка, на которую мы наткнёмся в первый же день.**
`ai-models/utils/is-provider-configured.util.ts:3-4`: поставщик регистрируется,
только если у него задан `apiKey`, либо `accessKeyId`, либо `authType`. Ollama
ключа не требует — и без ключа поставщик молча не появится в списке моделей.
**СЛЕДУЕТ ИЗ КОДА:** обход простой — вписать в `apiKey` любую строку-заглушку,
Ollama её игнорирует. Но узнать об этом можно только из кода: сообщения об ошибке
не будет, модель просто не появится в списке.

**СЛЕДУЕТ ИЗ КОДА. Обращение к модели не проходит сетевой фильтр.**
Twenty запрещает исходящие запросы на внутренние адреса
(`core-modules/secure-http-client/utils/is-private-ip.util.ts:5-23` — в чёрном
списке `127.0.0.0/8`, `192.168.0.0/16`, `10.0.0.0/8` и прочее; режим включён по
умолчанию, `config-variables.ts:103`). Но фабрика поставщиков
(`sdk-provider-factory.service.ts:118-139, 192-210`) **не** передаёт этот
защищённый клиент в библиотеку — используется обычный `fetch`. Значит адрес вида
`http://127.0.0.1:11434/v1` для модели разрешён, а для инструмента «сделать
HTTP-запрос» — запрещён. Это ровно то, что нам нужно, но по случайности, а не по
замыслу; при обновлении Twenty это надо перепроверять.

**ПРОВЕРЕНО.** Для OpenAI-совместимого поставщика **не подключается** встроенный
поиск в интернете: `ai-models/constants/native-model-tools-by-sdk-package.const.ts`
— для `@ai-sdk/openai-compatible` пустой набор. То есть с локальной моделью агент
физически не имеет инструмента «поискать в интернете» (у Anthropic, OpenAI и xAI —
имеет). Для нашего договора с НЛМК это хорошая новость.

**ПРОВЕРЕНО.** Ещё модель надо включить в рабочем пространстве
(`ai-models/utils/is-model-allowed.util.ts:8-22`) и не отключить в панели
администратора (`ai-models/services/ai-model-registry.service.ts:284-322`).
Стоимость своей модели каталог считает нулевой
(`ai-model-registry.service.ts:265-282` — цены 0/0), так что «кредиты» не сгорают.

**ПРОВЕРЕНО, и это единственный выход наружу в этой подсистеме.** Панель
администратора подтягивает подсказки по моделям с `https://models.dev/api.json`
(`ai-models/services/models-dev-catalog.service.ts:113`,
`ai-models/constants/models-dev.const.ts:1`). Запрос уходит только при открытии
экрана добавления поставщика, кеш на сутки, при недоступности сети пишется
предупреждение в журнал и экран работает без подсказок (`:117-135`). В закрытом
контуре это просто пустой список, не поломка.

## 5. Что именно уходит в модель

**ПРОВЕРЕНО. Запись целиком в модель не отправляется.** Когда сотрудник открыл
карточку и спросил что-то в чате, в сообщение подмешивается только это
(`ai-chat/services/chat-execution.service.ts:740-765`):

> «Пользователь смотрит запись типа `vehicle`, идентификатор такой-то, ссылка такая-то.
> При необходимости возьми детали инструментом.»

Ни одного значения поля. Данные модель получает, только если сама вызовет
`find_one_…`. То же для списка: имя представления, его идентификатор и словесное
описание фильтров (`:770-787`).

**ПРОВЕРЕНО.** Системная подсказка собирается из
(`ai-chat/services/system-prompt-builder.service.ts:135-177`):
базовых инструкций → инструкций рабочего пространства (их пишет администратор) →
контекста пользователя (имя, должность, язык, часовой пояс, сегодняшняя дата,
`:194-217`) → каталога инструментов → каталога навыков → списка загруженных файлов.

**ПРОВЕРЕНО. Бюджета контекста как настройки нет.** Есть подрезка по факту:
`ai-chat/services/message-pruning.service.ts:5, 18-51`. Когда разговор достигает
**90 % окна модели**, из него выбрасываются рассуждения модели и старые вызовы
инструментов (сохраняются последние два сообщения). Если резать больше нечего,
выставляется признак `isStillOverLimit` — и дальше решает вызывающий код.

**ПРОВЕРЕНО.** Размер оценивается грубо: `длина текста / 4`
(`system-prompt-builder.service.ts:34`, комментарий честно говорит «для смеси
английского и кода»).
**ПРЕДПОЛОЖЕНИЕ.** Для русского текста эта формула занижает размер: кириллица
обычно требует больше «кусочков» на символ. Значит на наших данных подрезка может
включиться позже, чем надо, и мы получим отказ модели «слишком длинный запрос»
вместо аккуратного сокращения. Проверять это надо замером, а не чтением.

## 6. Журнал запусков

Здесь картина неровная: три способа запуска — три разных уровня подробности.

**ПРОВЕРЕНО. Чат — записывается всё.** Три таблицы: `agentTurn` (ход разговора,
`ai-agent-execution/entities/agent-turn.entity.ts:18-53`), `agentMessage`, и
`agentMessagePart` (`entities/agent-message-part.entity.ts:40-117`) — где на каждую
часть ответа хранятся: тип, текст, рассуждения, **имя инструмента, его вход, его
выход, состояние, текст ошибки**, ссылки на источники, файлы, служебные данные
поставщика. Это полноценный след: кто что вызвал и что получил.

**ПРОВЕРЕНО. Рабочий процесс — записывается почти всё.**
`modules/workflow/.../ai-agent/utils/build-ai-agent-step-log.util.ts:24-43`
сохраняет в журнал шага: модель, токены (вход, выход, рассуждения, кеш, всего),
стоимость в долларах и в кредитах, число обращений к веб-поиску, длительность и
список вызовов инструментов. Вход каждого вызова обрезается на 32 КБ, выход — на
64 КБ, не более 200 вызовов на шаг
(`ai-agent-execution/utils/map-ai-steps-to-tool-call-logs.util.ts:10-13`).

**ПРОВЕРЕНО. Программный запуск `runAgent` — почти ничего.** Ни сообщений, ни
вызовов инструментов не сохраняется: `agent-run.service.ts:119-148` возвращает
результат вызывающему и на этом всё. Остаются только событие расхода
(`agent-async-executor.service.ts:568-595`: рабочее пространство, кредиты, всего
токенов, модель, тип операции, агент, сотрудник) и счётчики-метрики (`:392-452`).
**Прямое следствие для нас:** если «Пакетная проверка» будет гонять агента
программно, ответить на вопрос «почему по этому договору вышло вот так» будет нечем.

**ПРОВЕРЕНО.** Отдельно есть оценка качества: другая модель читает ход разговора и
ставит оценку с комментарием (`ai-agent-monitor/services/agent-turn-grader.service.ts:27-70`,
запись в `agentTurnEvaluation`). Полезно для настройки, но помните: **это ещё одна
отправка содержимого разговора в модель**.

## 7. Поиск по документам (RAG)

**ПРОВЕРЕНО. Его нет.** Поиск по всему серверному коду по словам `embedding`,
`pgvector`, `similarity_search`, `vector_store` не даёт ни одного попадания в
агентной части. Единственное, что находится, — полнотекстовый поиск PostgreSQL
(`tsvector`) по полям записей: это поиск по словам в карточках, а не по смыслу в
документах. Нет ни хранилища фрагментов, ни нарезки, ни ссылок на страницы.

**ПРОВЕРЕНО.** Ближайший по назначению механизм — **«навыки»** (skills):
именованные документы-инструкции. Модель видит список названий с описаниями в
системной подсказке и грузит нужный **целиком** по имени
(`tool-provider/tools/load-skill.tool.ts:36-64`). Никакой нарезки на фрагменты,
никакого отбора по релевантности.

**ПРОВЕРЕНО. Права к навыкам не применяются вообще — ни до, ни после.**
`skill.service.ts:231-243`: `findAllFlatSkills(workspaceId)` принимает только
рабочее пространство, фильтрует по признаку «активен» и всё. Вызывается так же —
`chat-execution.service.ts:169`. Значит любой навык доступен любому сотруднику с
правом на ИИ.

**Что это значит для нас, прямо:** функции «Вопрос по документу» и «Анализ
договора» на движке Twenty не строятся. Наш RAG остаётся на стороне сервиса
документов — что, кстати, совпадает с решением ADR-001 и усиливает его: тексты
договоров НЛМК вообще не попадают в базу Twenty, а значит и в её механизмы
раздачи. Ответственность за «кому какой документ можно» остаётся там, где она
сейчас и есть.

## 8. Может ли агент писать в базу мимо инструментов

**ПРОВЕРЕНО. Прямой SQL закрыт.** Метод `query()` у рабочего репозитория выбрасывает
исключение «метод запрещён» — `twenty-orm/repository/workspace.repository.ts:924-929`.
Через обычные инструменты обойти права нельзя.

**Но есть два обхода, и первый я называю риском прямым текстом.**

### Риск 1. Интерпретатор кода выдаёт модели пропуск сотрудника

**ПРОВЕРЕНО.** Инструмент `code_interpreter` выполняет Python, который **написала
модель**, в песочнице. Перед запуском он:

1. Выпускает пропуск (JWT) от имени сотрудника на 5 минут —
   `tool/tools/code-interpreter-tool/code-interpreter-tool.ts:307-324`;
2. Кладёт его и адрес сервера в переменные окружения песочницы — `:115-137`;
3. Подмешивает к коду модели готовый помощник `TwentyMCP`, который умеет вызывать
   **весь каталог инструментов** через служебный вход `/mcp` —
   `tool/tools/code-interpreter-tool/twenty-mcp-helper.const.ts` (в его же
   описании: «250+ инструментов CRUD / представлений / процессов / дашбордов»).

**ПРОВЕРЕНО.** А служебный вход `/mcp` определяет права **по роли сотрудника**, а
не по роли агента: `engine/api/mcp/services/mcp-protocol.service.ts:118-147`
берёт роль из `userWorkspaceId`.

**Итог, простыми словами.** Роль агента — это забор вокруг агента. Интерпретатор
кода даёт модели ключ от калитки в этом заборе: код, который она сама написала,
работает уже не с правами агента, а с правами позвавшего человека. Если у бухгалтера
есть право удалять платежи, то агент, которому это право не давали, сможет их
удалить — достаточно, чтобы модель написала три строки на Python.

Забор всё-таки не нулевой: инструмент включается только флагом роли
`CODE_INTERPRETER_TOOL` и только если сама песочница настроена
(`action-tool.provider.ts:187-193`). **Рекомендация: не включать этот флаг никому.**
Наши задачи с Excel решает сервис документов, а не песочница внутри Twenty.

### Риск 2. Логические функции вызываются без проверки прав

**ПРОВЕРЕНО** (подробности в разделе 3). Логическая функция, помеченная как
инструмент, попадает в каталог всем и вызывается с одним лишь идентификатором
рабочего пространства — `tool-executor.service.ts:283-307`. Внутри функции можно
делать что угодно; ограничивать себя она должна сама.

**Смягчающее обстоятельство. ПРОВЕРЕНО.** Для агентов, запускаемых в рабочих
процессах и программно, набор категорий инструментов сужен до двух — записи и
действия (`ai-agent-execution/constants/workflow-agent-registry-tool-categories.const.ts:3-6`).
Логические функции туда не входят. То есть обход открыт **в чате**, а не в
автоматических сценариях.

## Что это значит для переноса

**1. Агентный движок брать, не писать свой.** Он даёт ровно то, ради чего мы бы
писали месяцы: цикл «подумал — вызвал — подумал», инструменты со строгими схемами
входа, роли, журнал, потоковую выдачу в интерфейс, оценку качества. Из наших
двадцати двух функций на него хорошо ложатся три (№ 1 «Проверка документа»,
№ 3 «Вопрос по документу», № 4 «Пакетная проверка») — при условии, что тяжёлая
часть остаётся в сервисе документов.

**2. Ollama — да, но три действия обязательны.** Шаг за шагом:
   - в `AI_PROVIDERS` завести поставщика с `npm: "@ai-sdk/openai-compatible"` и
     `baseUrl` нашего Ollama;
   - **обязательно** вписать в `apiKey` строку-заглушку, иначе поставщик молча не
     появится (`is-provider-configured.util.ts:3-4`);
   - модель включить в настройках рабочего пространства, иначе запуск отклонят
     (`is-model-allowed.util.ts:8-22`).
   Встроенного веб-поиска у такой модели не будет — это ровно то, что требует
   договор с НЛМК.

**3. Обещание «наружу ничего не уходит» стало проверяемым в четырёх местах, а не
в одном.** Раньше был `netguard` и один процесс. Теперь надо закрыть:
   - флаг роли `HTTP_REQUEST_TOOL` (инструмент «сделать запрос») — не выдавать;
   - флаг роли `CODE_INTERPRETER_TOOL` — не выдавать;
   - инструмент `search_help_center` — он выдан **всем без флага** и отправляет
     текст запроса сотрудника на внешний сервис
     (`tool/tools/search-help-center-tool/search-help-center-tool.ts:37-52`);
     закрыть его можно только на уровне сети или правкой ядра;
   - подтягивание каталога с `models.dev` в панели администратора — безобидно, но
     в отчёте о сетевой активности оно всплывёт, и это надо объяснить заранее.

**4. Наш сервис документов подключать логической функцией — с оговоркой.**
Технически это работает: логическая функция с настройкой «вызывается как
инструмент» автоматически становится инструментом агента с именем `app_…` и схемой
входа (`logic-function-tool.provider.ts:75-104`). Но прав она не проверяет вовсе,
поэтому **проверку «кому можно» надо делать внутри самой функции**, а не надеяться
на роль. Заодно факт: предел времени логической функции — 900 секунд, 15 минут
(`logic-function-drivers/drivers/local.driver.ts:113`,
`.../lambda/constants/lambda-driver.constant.ts:16`), и он настраивается на каждую
функцию (`logic-function-executor.service.ts:164`). Это ответ на вопрос,
поставленный в ADR-001: пятнадцати минут хватит и на книгу Excel, и на договор.

**5. Роль агента проектировать сразу, а не потом.** Права агента — это его роль,
и ничего кроме. Разумная отправная точка: отдельная роль «Помощник по документам»
с правом читать нужные объекты, без права на удаление, без всех четырёх флагов
опасных инструментов. Пересечение с ролью сотрудника система обеспечит сама.

**6. «Подтверждение перед записью» придётся строить самим.** Его в движке нет.
Если реестр на оплату или закрытие месяца должны утверждаться человеком — это
отдельный объект «на утверждении» и шаг рабочего процесса, а не надежда на строчку
в подсказке модели.

**7. Для программных запусков журнал придётся заводить свой.** `runAgent` не
сохраняет ни вопрос, ни вызовы инструментов. Если «Пакетная проверка» пойдёт этим
путём, объяснить бухгалтеру задним числом, почему по счёту вышло именно так, будет
нечем. Либо пускать через рабочий процесс (там журнал есть), либо писать свой.

## Риски

**Модель удалит или испортит записи, и никто не заметит вовремя.**
Все инструменты изменения — `update_many_…`, `delete_many_…` — доступны сразу, как
только у роли есть право на изменение, и выполняются без подтверждения. В описании
инструмента стоит слово «ВНИМАНИЕ, используйте узкие фильтры»
(`database-tool.provider.ts:349, :430`) — но это текст для модели, а не проверка.
*Чем грозит:* инженер просит «закрой все просроченные заявки», модель ошибается в
фильтре и закрывает все заявки вообще. Удаление мягкое, восстановимое
(`tool-executor.service.ts:208` — `soft: true`), а вот массовое изменение полей —
нет. Живой пример из нашего же опыта: дефект «в назначение платежа вместо суммы НДС
попадает ставка» нашли тестами, а не глазами. Здесь тестов не будет — будет модель.

**Интерпретатор кода превращает роль агента в декорацию.** Разобрано в разделе 8.
*Чем грозит:* бухгалтер задаёт агенту безобидный вопрос, модель решает «посчитаю
питоном», и код работает с полными правами бухгалтера — включая всё, что агенту
никогда не давали. Лечится одним действием: не выдавать флаг `CODE_INTERPRETER_TOOL`.

**Текст запроса уходит наружу через справочный поиск.** `search_help_center` выдан
всем без всякого флага и отправляет введённый текст на внешний адрес
(`search-help-center-tool.ts:37-52`). *Чем грозит:* секретарь пишет в чат «почему
не открывается договор с НЛМК на поставку», модель решает поискать в справке — и
эта фраза уходит на чужой сервер. Штраф в договоре предусмотрен именно за это.
Лечится закрытием исходящих соединений на уровне сети — кодом внутри Twenty не лечится.

**Логическая функция как инструмент доступна всем.** *Чем грозит:* если «Анализ
договора» подключён логической функцией, его сможет запустить любой сотрудник с
правом на ИИ, включая тех, кому договоры видеть не положено. Лечится проверкой
внутри самой функции.

**Триста шагов — это долго и дорого.** `AGENT_CONFIG.MAX_STEPS = 300`. *Чем грозит:*
с локальной моделью на нашем железе один заблудившийся запуск способен занять
процессор надолго, а сотрудник в это время смотрит на «думаю…». Ограничение
задано константой в коде, настройкой не выносится — менять придётся правкой ядра.

**Подрезка контекста может сработать слишком поздно на русском тексте.**
Оценка «4 символа = 1 токен» для кириллицы оптимистична. *Чем грозит:* длинный
разговор внезапно заканчивается ошибкой модели вместо аккуратного сокращения.
Это надо замерить на настоящих данных до запуска, а не после.

**«Оценка качества» — это ещё одна отправка разговора в модель.** Если модель
локальная, ничего страшного. Если кто-то когда-нибудь переключит рабочее
пространство на облачную модель ради качества — переписка уедет туда дважды.

## Открытые вопросы

1. **Куда попадает событие расхода?** `emitAiTokenUsageEvent`
   (`ai-billing.service.ts:174-205`) шлёт событие `USAGE_RECORDED` в общую шину.
   Кто его слушает и пишет ли в базу или в ClickHouse — не проследил. Если оно
   нигде не оседает, у нас нет ответа на вопрос «сколько ИИ отработал за месяц».

2. **Уходят ли подсказки и ответы в трассировку?**
   `ai-models/constants/ai-telemetry.const.ts:1-5` включает трассировку с записью
   входов **и выходов**. Приёмник (OpenTelemetry) в исходниках сервера я не нашёл —
   значит, скорее всего, они никуда не отправляются. Но это надо подтвердить на
   настоящей сборке: если приёмник появится в контейнере, тексты договоров окажутся
   в трассировке.

3. **Как ведёт себя Ollama при вызове инструментов?** В коде есть отдельный
   «ремонт» неудачных вызовов (`ai-agent/utils/repair-tool-call.util.ts`) и
   заплатка специально для Gemini. Насколько локальная модель уровня 8–14 млрд
   параметров вообще способна корректно вызывать инструменты со сложными схемами —
   вопрос замера, а не чтения кода. Это главный технический риск всего замысла: если
   локальная модель не умеет надёжно вызывать инструменты, агентный движок Twenty
   нам не пригодится, каким бы хорошим он ни был.

4. **Можно ли отключить `search_help_center` без правки ядра?** Он добавляется
   безусловно. Механизма «убрать инструмент из каталога настройкой» я не нашёл;
   есть только список исключений для агентов в рабочих процессах
   (`workflow-agent-excluded-tool-names.const.ts`), но не для чата.

5. **Что происходит при `isStillOverLimit`?** `message-pruning.service.ts:48`
   выставляет признак «подрезать больше нечего». Как на него реагирует вызывающий
   код и что видит человек — не прослежено.

6. **Сохраняются ли ходы чата, если модель оборвалась на середине?** В коде есть
   удаление хода при ошибке (`agent-chat.service.ts:457, :643`). Останется ли в
   журнале след неудачного запуска — не проверял. Для разбора «почему не сработало»
   это важно.
