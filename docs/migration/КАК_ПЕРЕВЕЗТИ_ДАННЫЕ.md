# Как перевезти данные из старой программы в новую

Для того, кто будет это делать руками: ИТ-администратор компании или
разработчик. Читать целиком до первого запуска — здесь есть места, где ошибка
исправляется тяжело.

Программа-перевозчик:
`apps/backend/src/fire_safety_backend/perenos_v_twenty.py` в хранилище
ассистента.

---

## Что она делает

Читает старую базу и заводит те же записи в новой системе: контрагентов,
машины, водителей, прицепы, точки, договоры, огнетушители, путевые листы, рейсы
и строки прицепов в листах — одиннадцать таблиц.

**Она не трогает старую программу.** Та продолжает работать как работала: из
базы только читают.

---

## Главное, что надо знать заранее

### Запускать заново можно и нужно

Перевозка большой базы с первого раза не проходит почти никогда: где-то
незнакомый код, где-то пустая графа, где-то оборвалась связь. Это нормально.

Повторный запуск **не заводит записи заново**. У каждой записи есть отметка
«приехала из старой базы, номер там такой-то», и вторую такую же система не
принимает. Держит это сама база, а не аккуратность программы.

### Удалённая запись мешает и не возвращается

Если запись из новой системы удалить, она уезжает в корзину — но свою отметку
держит по-прежнему. Повторная перевозка на неё скажет «такая уже есть» и
пропустит. **В списке при этом пусто, и запись не появится больше никогда.**

Перевозчик такое различает и пишет отдельно: `ЛЕЖАТ В КОРЗИНЕ`. Если это
увидели — запись надо либо восстановить из корзины, либо стереть из корзины
окончательно, и только потом запускать перевозку снова.

Именно поэтому обычным сотрудникам удаление записей не выдано вовсе.

### Данные заказчика в журнал не попадают

Перевозчик печатает только числа и номера записей. Наименований, реквизитов и
фамилий в выводе нет — журнал могут читать посторонние. Если запись не поехала,
её ищут в старой базе по номеру.

## Порядок работ

### Шаг 1. Снимок базы

Обязательный, не «желательно». Перевозка пишет в живую базу.

```bash
pg_dump -d default > снимок-до-перевозки.sql
```

### Шаг 2. Пропуск в новую систему

Перевозчику нужен пропуск — иначе она откажется работать. Пропуск живёт не
вечно; если он истечёт посреди перевозки, будет написано ровно это, и надо
просто взять новый и запустить заново.

```bash
export POZH_TWENTY_URL=http://адрес-сервера:3000
export POZH_TWENTY_TOKEN=пропуск-от-ит-администратора
```

### Шаг 3. Посмотреть, сколько поедет

Ничего не меняет, только считает.

```bash
python -m fire_safety_backend.perenos_v_twenty --база путь/к/base.db --посмотреть
```

### Шаг 4. Перевезти

```bash
python -m fire_safety_backend.perenos_v_twenty --база путь/к/base.db
```

### Шаг 5. Дозаполнить связи

Нужен, если в отчёте были строки `без связи`. Так бывает, когда запись приехала
раньше той, на которую ссылается.

```bash
python -m fire_safety_backend.perenos_v_twenty --база путь/к/base.db --дополнить
```

**Дозаполнение трогает только пустые графы.** Если между заездами человек
поправил адрес или телефон в новой системе, его правка останется. Это
проверяется отдельно и нарочно: затёртая правка — худший исход, человек её не
заметит, а в счёт уйдёт старое.

---

## Что означают строки отчёта

| Строка | Что это значит | Что делать |
|---|---|---|
| `заведено 12` | двенадцать записей переехали | ничего |
| `уже были 12` | они переехали раньше | ничего, это обычное дело при повторе |
| `дополнено 3` | у трёх записей дозаполнены пустые графы | ничего |
| `без связи 2` | две записи завелись, но ссылка осталась пустой | прогнать `--дополнить` после того, как переедет то, на что ссылаются |
| `ЛЕЖАТ В КОРЗИНЕ 5` | пять записей есть в корзине и потому не заводятся | восстановить из корзины или стереть окончательно |
| `НЕ ПОЕХАЛИ 1` | отказ, ниже написан номер записи и причина | см. ниже |

## Самый частый отказ: незнакомый код

Выглядит так:

```
запись №907: Invalid value "GODEN" for field "state".
Valid values are: SERVICEABLE, ON_RECHARGE, WRITTEN_OFF
```

Значит, в старой базе состояние записано одним словом, а новая система ждёт
другое. Это **не поломка** — перевозчик нарочно останавливается вместо того,
чтобы подставить похожее: состояние огнетушителя решает, выпустят ли его в
работу.

Что делать: открыть `perenos_v_twenty.py`, найти правило нужной таблицы и
дописать строчку в `перевод`:

```python
перевод={"state": {"в работе": "SERVICEABLE", "GODEN": "SERVICEABLE"}},
```

Список допустимых значений печатается в самом отказе — гадать не надо.

Разницу в написании (`OP5` против `OP_5`) перевозчик разбирает сам, дописывать
такое не нужно.

## Чего перевозчик НЕ делает

Это не недоделки, а решения — но знать их надо.

- **Не переносит 82 графы путевого листа из 98.** Перенесены 13 граф и три
  связи — те, для которых в новой системе есть поле. Числа посчитаны по коду,
  а не на глаз. Осталось за бортом: медосмотр до и после рейса,
  техконтроль выпуска, итоги смены (простои, тонно-километры, расход по норме),
  зарплата, таксировка, часть цепочки по топливу. Пока эти графы не заведены в
  новой системе, лист там юридически неполон.
- **Не связывает рейс с водителем напрямую.** В старой базе водитель у рейса
  записан фамилией, а не номером. Связывать по фамилии — значит молча ошибаться
  на однофамильцах. Водитель у рейса берётся через путевой лист, там номер
  настоящий.
- **Не переносит простои на линии** — в новой системе для них нет объекта.
- **Не удаляет ничего** ни в старой базе, ни в новой.

---

## Если что-то пошло совсем не так

Восстановить снимок:

```bash
psql -d default < снимок-до-перевозки.sql
```

После восстановления перевозку можно запускать с начала: отметки «приехала из
старой базы» вернутся вместе со снимком, и повторов не будет.
